With shadows enabled, a Vectreal scene accumulates its directional shadow over 48 frames while you are composing it in the Publisher, then stores the settled result as a PNG. When someone loads the published embed, the viewer draws that stored texture on a plane and never runs the accumulation at all.

What that looks like from the outside is written up in [adding shadows to a 3D model on your website](https://vectreal.com/news-room/adding-shadows-to-a-3d-model-on-your-website). This is the underneath: why the split exists, and what it cost to build.

## Why not just use contact shadows

For a while that is exactly what the viewer did. drei's `ContactShadows` is a depth pass blurred into a texture, cheap, live, and it tracks a model that moves. It also produces a soft pool under the model and nothing else. There is no directional cast, so the object reads as floating slightly above the surface instead of sitting on it.

`AccumulativeShadows` does read correctly. It builds a lightmap by accumulating many passes of a jittered light, which is what gives you a real penumbra instead of a blur. drei's default is 40 frames and `temporal` off; the Publisher runs 48 with `temporal` on so the shadow fades in over several frames rather than hitching the first one.

The cost lands in the wrong place, though. Composing a scene, you are already waiting, and 48 frames is nothing. On an embed sitting in someone's product page, every visitor pays for 48 frames of accumulation to arrive at the same shadow every time. The scene is static and the light does not move. Recomputing it per visitor is work with a known answer.

So the bake happens once, where someone is already waiting, and everywhere else loads the answer. The viewer source is at [github.com/Vectreal/vectreal-platform](https://github.com/Vectreal/vectreal-platform?utm_source=newsroom&utm_medium=article&utm_campaign=shadow-bake) if you want to read along.

## What actually gets stored

Not a picture of the shadow. A density mask.

drei's `SoftShadowMaterial` derives the shadow's alpha from the baked lightmap's brightness, then multiplies by opacity and tints by color. If I stored the finished shadow, then changing how dark or what color it is would mean baking again. Those are the two controls people reach for most, and they are also the two that have nothing to do with the geometry.

So the capture pass re-renders the accumulated lightmap through a shader that keeps only the density term, writes it to the alpha channel, and leaves RGB black:

```glsl
varying vec2 vUv;
uniform sampler2D uMap;
uniform float uAlphaTest;
void main() {
	vec3 c = texture2D(uMap, vUv).rgb;
	float density = max(0.0, 1.0 - (c.r + c.g + c.b) / uAlphaTest);
	gl_FragColor = vec4(0.0, 0.0, 0.0, density);
}
```

At load time a plane samples that alpha and applies the live values on top:

```glsl
float density = texture2D(uMap, vUv).a;
gl_FragColor = vec4(uColor, density * uOpacity);
```

Opacity and color stay adjustable forever, at no cost. The stored file is 512 px square, which is small because it is base64-inlined into the scene aggregate and rides along with the model data instead of costing a second request. A soft shadow is low-frequency and downscales cleanly, so it survives that, but it is a ceiling and I know it.

## Knowing when the bake has gone stale

A stored bake is only correct for the exact inputs that produced it, so each one carries a signature: an FNV-1a hash over a canonically ordered serialization of every input that changes the density. Light position, radius, ambient, amount, intensity, bias, plus frame count, plane scale, resolution, alphaTest, colorBlend and cutoffScale. Then a fingerprint of the model itself, from its footprint, bounding radius and total vertex count, so that swapping in a different model that happens to share a bounding box still invalidates the bake.

`opacity` and `color` are deliberately absent from that list, for the reason above.

An earlier version of the signature was a hand-written list of fields and it quietly omitted three of them. Serializing the complete input set and hashing it is what caught it, and the token carries a `v2:` prefix so older ones mismatch and trigger a single re-bake rather than colliding. The list is still hand-authored, so a future option added without a matching line would reintroduce the same gap.

The reason a signature is needed at all, rather than baking again and comparing, is that the bake is not deterministic. `RandomizedLight` jitters, so two bakes of an unchanged scene are never byte-identical. Without the signature, every save would upload a new PNG that looks the same as the last one.

## The part that cost the most time

`AccumulativeShadows` resets and re-bakes inside a layout effect that has no dependency array, so it re-bakes on every render it performs. In the Publisher, opening the shadow tool flips a prop that mounts the light handle, which re-renders the parent, which wiped the bake and started it over. Adjusting a shadow reset the shadow.

The fix is to memoize the bake subtree so the element stays referentially stable and only changes when a real bake input changes. React then skips re-rendering it, and the bake survives everything happening around it. Same treatment for the contact shadow underneath, for the same reason.

## What is still rough

Shadows are off by default, so this is opt-in rather than something every scene gets.

The contact shadow renders in both branches, outside the persisted-bake conditional, so a scene with the ground shadow enabled still runs one `ContactShadows` depth pass at load. It is `frames={1}` and one-time rather than per-frame, but the embed is only fully free of shadow work when that option is off.

If a model's geometry is animating, the viewer drops back to live contact shadows for the duration, because a baked plane lags geometry that moves. Camera auto-rotate is fine, since that orbits the camera and leaves the model still.

Any change to a bake input re-bakes, which is correct but does mean the first save after changing a shadow setting is slower than the ones after it. And the 512 px ceiling is a judgement call I may have to revisit for large scenes.

All of this is pre-1.0 and the shape of it may still change. If you want to see how it fits together, the shadow components live under `packages/viewer/src/components/scene/` in [github.com/Vectreal/vectreal-platform](https://github.com/Vectreal/vectreal-platform?utm_source=newsroom&utm_medium=article&utm_campaign=shadow-bake).
